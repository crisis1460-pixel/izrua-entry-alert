## 1. 역신호(Reverse Signal)란 무엇인가

### 1-1. 개념 정의

역신호는 "이 작성자의 신호를 따르면 기대손익이 음수"라고 통계적으로 판정된 상태다.  
구체적인 판정 조건은 다음 두 가지를 **2주 연속** 만족하는 것이다:

- `neff_r >= 5`: R-트랙 유효표본이 5 이상 (손절 기재 신호의 종결 표본)
- `E_LB < 0`: 보수적 기대 R-멀티플이 0 미만

**E_LB(보수적 기대값)**은 `analytics/ranking.py:46`에 정의된다:

```
E_LB = mean_w − 1.28 × √(var_w / n_eff)
```

가중 평균 R에서 80% 단측 신뢰 하한을 뺀 값이다. "운 좋은 표본이어서 플러스처럼 보이는" 경우를 걸러내는 보수적 추정치다.  
`n_eff`는 Kish 유효표본수(최신 신호에 더 많은 가중치)로, 단순 건수 대신 최신성 감쇠를 반영한다.

### 1-2. 역신호 후보 vs 역신호 확정

| 상태 | 조건 | 현재 구현 |
|------|------|-----------|
| 역신호 후보 | 현 시점 neff_r≥5 이면서 E_LB≤0 | `show_status.py:311` 🔻역신호후보 태그, 주간 리포트 "역신호 후보 N명" |
| **역신호 확정** | 2주 연속 후보 | **미구현 — 이 문서의 주제** |

단기 손실 연속은 정상 편차(임의성)일 수 있다. "2주 연속"은 일시적 슬럼프와 구조적 문제를 구분하기 위한 안전마진이다.

## 2. 현재까지 구현된 것과 미완성인 것

### 2-1. 구현 완료된 인프라

**스냅샷 축적 (`run_cycle.py:303–333`, `storage/db.py:95–107`)**

- 매 7일(`author_snapshot_interval_hours=168`)마다 `take_author_snapshot()`이 실행된다.
- 모든 종결 표본을 가진 작성자의 현 시점 지표(`e_lb`, `neff_r`, `p_hat`, `neff_win`, `wins`, `losses`)를 그 주차(ISO week, KST 기준)로 `author_snapshots` 테이블에 저장한다.
- 저장 전용 — 알림·필터·등급 어디에도 영향을 주지 않는다.

**실시간 E_LB 주입 (`price_check.py:613–624`)**

- 알림 발송 직전 `ranking.author_metrics()`를 호출해 `lv["author_self_e_lb"]`를 레벨 dict에 주입한다.
- 렌더러(`telegram.py:234`)는 이 값을 알림 본문에 표시하지 않는다 (2026-07-27 사용자 결정 — 알림이 너무 길어진다는 이유로 당일 되돌림).

**현황 표시 (`show_status.py:311`, `telegram.py:444–449`)**

- `show_status --report` 실행 시 E_LB≤0인 작성자에 🔻역신호후보 태그 표시.
- 주간 리포트: E_LB≤0이면서 n_eff 게이트 통과 작성자를 🔻 표기 + 본문 하단 "역신호 후보 N명" 안내.
- `show_status.py:327–351`: 최근 2주 스냅샷 추이를 비교해 E_LB 변화 방향(▲▼─)을 출력.

**저장 함수 (`storage/db.py:541–559`)**

- `save_author_snapshot(conn, week, author, met, now)` — 주차·작성자 기본키, 재실행 시 덮어쓰기.
- `get_author_snapshots(conn, author=None, limit_weeks=8)` — 작성자별 또는 전체 최근 N주 조회.

### 2-2. 미완성인 것

다음 기능이 아직 없다:

1. **2주 연속 판정 함수**: `author_snapshots`에서 특정 작성자의 직전 2주를 꺼내 "두 주 모두 neff_r≥5 이고 e_lb<0인가"를 확인하는 순수 함수.
2. **확정 시 액션 정의**: 확정 작성자에 대해 무엇을 할지(알림 억제, 경보, 리포트 표시 강화 등) 결정되지 않았다.
3. **확정 경보 알림 형식**: 역신호 확정 시점에 사용자에게 어떤 텔레그램 메시지를 보낼지 정해지지 않았다.
4. **테스트**: 역신호 최종 판정 로직에 대한 테스트 케이스가 없다.

## 3. 스냅샷 2주치가 왜 필요한가

### 3-1. 기다리는 데이터

| 스냅샷 | 주차 | 예상 저장 시점 |
|--------|------|---------------|
| 1차 | 2026-W30 | 2026-07-26 (이미 저장됨) |
| 2차 | 2026-W31 | 2026-08-02 전후 |

"2주 연속" 판정은 **현재 주 스냅샷**과 **직전 주 스냅샷**을 비교해야 한다.  
현재(2026-07-30) `author_snapshots`에는 W30 데이터만 있다. W31 스냅샷이 저장되는 2026-08-02 이후부터 판정이 가능하다.

### 3-2. 왜 "8월 중순"인가

HANDOFF.md §8이 "8월 중순"을 적은 것은 여유 마진이다:
- 2주치 스냅샷은 8월 초에 충족된다.
- 그러나 종결 표본도 충분히 쌓여야 `neff_r >= 5` 게이트를 넘는 작성자가 실제로 나온다.
- 현재 미판정 43건 중 17건이 07-30~08-10 사이에 판정 도래 예정(`2026-07-28_감시_중간보고.md` §4).
- 두 가지가 동시에 만족되는 시점이 8월 중순 전후일 가능성이 높다.

## 4. 구현 설계안

### 4-1. 파일·함수 단위 변경 목록

**A. `storage/db.py`에 조회 함수 추가**

```python
def get_author_last_n_snapshots(conn, author: str, n: int = 2) -> list:
    """최근 N 주차 스냅샷을 최신순으로 반환. 역신호 연속 판정용."""
    rows = conn.execute(
        "SELECT * FROM author_snapshots WHERE author=? "
        "ORDER BY week_kst DESC LIMIT ?",
        (author, n)
    ).fetchall()
    return [dict(r) for r in rows]
```

기존 `get_author_snapshots()`와 구분해 역신호 판정 전용 함수로 분리한다.  
이유: 기존 함수는 전체 조회 또는 다수 주차 조회용이고, 이 함수는 "최근 2주만 빠르게"가 목적이다.

**B. `analytics/ranking.py`에 판정 순수 함수 추가**

```python
def is_confirmed_reverse(snapshots: list, min_neff: float = 5.0) -> bool:
    """최근 N개 스냅샷(최신순)이 모두 neff_r>=min_neff 이고 e_lb<0 이면 True.
    
    순수 함수 — DB 접근 없음. 스냅샷이 2개 미만이면 False(증거 부족).
    n 주 연속 판정으로 확장하려면 snapshots 길이만 늘리면 된다."""
    if len(snapshots) < 2:
        return False
    return all(
        (s.get("neff_r") or 0) >= min_neff and (s.get("e_lb") is not None) and s["e_lb"] < 0
        for s in snapshots
    )
```

이 모듈은 이미 "프로젝트 모듈 import 0" 원칙을 지키는 순수 함수 집합이므로 여기에 추가가 자연스럽다.

**C. 확정 후 액션 (결정 필요 — 아래 옵션 참조)**

이 부분은 사용자 결정 후 구현한다. 후보 통합 위치는:

## 5. 확정 후 액션 옵션 (결정이 필요한 항목)

### 옵션 A: 알림 억제

확정 역신호 작성자의 레벨은 터치돼도 텔레그램 알림을 보내지 않는다.

- 장점: 신뢰도 낮은 신호를 자동으로 걸러낸다.
- 단점: 사용자가 "왜 알림이 안 오는지" 모를 수 있다. 관찰기 원칙("알림량에 영향 주는 변경 금지")에 저촉될 가능성이 있다.
- 구현 위치: `price_check.py`의 `send_ok` 판정부 (현재 `meets_min_grade`·`daily_cap`·재발송 차단과 같은 자리).
- 추가 통계 컬럼 필요: `daily_stats`에 `suppressed_reverse_author INTEGER DEFAULT 0`.

### 옵션 B: 일회성 확정 경보 (추천)

확정 시점에 텔레그램으로 경보를 1회 발송하고, 알림 필터는 건드리지 않는다.

- 장점: 사용자가 인지하면서도 직접 판단하는 구조 유지. 알림량에 영향 없음.
- 단점: 후속 조치(그 작성자 신호를 계속 받을지)는 수동으로 결정해야 한다.
- 구현 위치: `run_cycle.py`의 스냅샷 훅 직후, 새 `_maybe_reverse_alert()` 함수.
- 중복 방지: `meta` 테이블에 `reverse_signal_alerted_{author}_{week}` 키 저장.

### 옵션 C: 리포트 전용 표시

주간 리포트와 `show_status`에만 "역신호 확정" 구분을 추가하고, 실시간 알림에는 영향 없음.

- 장점: 구현이 가장 단순하고 안전하다.
- 단점: 주간 리포트가 꺼져 있어(`자동발송 OFF`) 현재 이 채널이 비어 있다.

**관찰기 원칙 (현재 최중요)**

**`neff_r` 게이트 의미 (2026-07-27 확정)**
