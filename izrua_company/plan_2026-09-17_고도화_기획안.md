## 0. 이번 분석의 결론 한 줄

**등급 점수(`touch_score`)는 같은 판정축 안에서 승패를 못 가린다(r = −0.028).**
그래서 "경계를 다시 긋자"(09-13 Q1)는 계획은 **알림 품질을 1%p도 못 바꾼다.** 대신
`judgment_mode` 교란을 걷어내자 **수집→터치 지연**이라는 검증된 신호가 드러났고,
MFE/MAE 컬럼은 계산 버그로 통째로 무효였다.

## 1. 교차검증한 사실 (CTO 재쿼리)

### 1-1. 🚨 등급 점수의 예측력은 판정축 교란이 만든 착시였다

| judgment_mode | n | 점-이연 상관 r | 승자 평균점 | 패자 평균점 |
|---|---|---|---|---|
| **tp_sl** (SL 있음 — 유일하게 공정한 축) | 73 | **−0.028** | 45.6 | 46.2 |
| tp_only (SL 없음 → miss 불가) | 64 | −0.266 | 53.9 | 58.5 |
| timeboxed | 32 | +0.377 | 38.6 | 31.3 |
| 전체(층화 안 함) | 169 | **+0.226** | 50.0 | 44.6 |

전체 r = +0.226 은 "점수가 높으면 잘 맞는다"처럼 보이지만, **tp_sl 안에서는 −0.028 로
사실상 0**이다. tp_only 는 오히려 **점수가 높을수록 나쁘다**(−0.266). 즉 지금까지의
등급 신뢰는 "SL 안 쓰는 작성자가 고득점이고, 그 글은 구조적으로 miss 가 안 난다"는
사실을 예측력으로 오독한 것이다.

> **따라서 09-13 기획안의 Q1(등급 경계 재보정)은 목적을 바꿔야 한다.** 경계를 옮겨도
> 승률은 안 움직인다. 재보정의 가치는 **표시 정상화**(S·A 부활)뿐이며, 예측력은
> 산식에 **새 피처를 넣어야** 생긴다.

### 1-2. ✅ 유일하게 검증된 신호 — 수집→터치 지연 (tp_sl 한정)

| 지연 | n | 승률 | Wilson LB80 |
|---|---|---|---|
| **< 30분** | 81 | **25.9%** | 20.2% |
| 30분~3h | 18 | 27.8% | 16.6% |
| 3~24h | 46 | 37.0% | 28.4% |
| **24h+** | 39 | **48.7%** | 38.7% |

격차 **+22.8%p**, 단조 증가, 양 끝 n≥20, **LB80 구간이 겹치지 않는다**(20.2 vs 38.7).
`judgment_mode` 층화를 통과한 유일한 신호다.

의미: **글이 올라오자마자 닿는 진입가는 이미 지나간 자리**다. 반대로 하루 이상 기다려
닿은 자리는 작성자가 실제로 계산한 지점일 가능성이 높다. 결측 0%, 계산 비용 0
(`touched_at − collected_at`, 이미 DB 에 있음).

**부수 효과**: 현재 tp_sl 종결의 **43%(81/188)가 최악 구간(<30분)**이다. 이걸 감점하면
알림량도 함께 줄어든다 — 아래 §2-2 의 알림량 문제와 한 번에 풀린다.

### 1-3. 🚨 신규 버그 — MFE/MAE 가 "종결 직전 몇 분"만 잰다

| | 실측 |
|---|---|
| 승리 건 중 `mae_pct == 0` | **118/120 (98.3%)** |
| 패배 건 중 `mfe_pct == 0` | **118/121 (97.5%)** |

코드 확인(`monitor/price_check.py` 1852~1870, 2079~2090): `_running_mfe/_running_mae` 가
**매 회차 0.0 으로 초기화**되는데, 스캔 대상 캔들은 `upbit.fetch_range_since(ticker,
since_min, …)` 즉 **직전 회차 이후(≈4~6분)** 구간뿐이다. `record_mfe_mae` 는 종결 시점에
한 번만 호출되므로, 결국 **종결이 일어난 그 회차의 몇 분**만 기록된다.

TP 로 종결되면 그 몇 분간 상승만 있어 `mae=0`, SL·타임박스면 하락만 있어 `mfe=0` —
관측된 98% 패턴과 정확히 일치한다.

**영향**: `mfe_pct`·`mae_pct`·`touch_mfe_atr_ratio`(F1) 전부 무효. 이 값을 쓴 분석
(09-13 보고서의 MFE/MAE 표, 터치 품질 버킷)도 **근거로 쓸 수 없다**.

### 1-4. A안 실적 — 총량은 성공, 진입 알림은 안 줄었다

| 구간 | 실발송/일 | 그중 touch |
|---|---|---|
| A안 전(09-01~12) | **16.67** | 5.83 |
| A안 후(09-14~16, 완전한 3일) | **6.67** | **6.67** |

총량 **−60%** 는 달성(TP·뉴스를 브리핑으로 흡수한 덕). 그러나 진입 알림 자체는
5.83 → 6.67 로 **늘었다**. 목표(≤5/일)를 넘는 건 시장 활성도보다 **게이트가 느슨해서**다 —
`alert_min_grade='C'` 에서도 터치의 74% 가 통과한다.

### 1-5. 부작용 점검 — 이상 없음

`pending_tp` 0행 · `sent=0` 정상 누적 · 뉴스 큐 전건 소비(유실 0) · touch 중복 0 ·
short 수집 09-13 22:27 이후 0건. A안·Q3 배포는 깨끗하다.

단 **뉴스 5건 쿼터가 00~04시에 도착순으로 소진**된다 — 브리핑의 5건은 "중요한 5건"이
아니라 "먼저 온 5건"이다.

## 2. 제안 (우선순위 순)

### P1. MFE/MAE 계산 수리 — **다른 모든 것의 선행 조건**
지금 상태로는 터치 품질·R 분포·가상 손절 시뮬레이션 어느 것도 정본으로 못 쓴다.
- **수리안**: 회차마다 `levels.mfe_pct/mae_pct` 를 **더 극단값으로 갱신**(현재는 종결 시 1회 기록).
  터치 이후 전 구간이 자연히 누적된다. 추가 API 콜 0 — 이미 그 캔들을 읽고 있다.
- 과거 데이터는 소급 불가(캔들 재조회 비용) → **기록 시작 시점을 명시**하고 이후 표본만 분석에 사용.
- 공수 S. 결정 불필요 — 명백한 버그.

### P2. 수집→터치 지연을 등급 산식에 투입
- **안 A(추천)**: `touched_at − collected_at < 30분` 이면 **−6점**(사다리 감점 −3 의 2배).
  근거 격차가 사다리(+4.1%p, §1-1 재산정)의 5배 이상.
- **안 B**: 구간별 차등(−6 / −3 / 0 / +3).
- 주의: 이 값은 **터치 시점에만 확정**되므로 수집 시점 등급이 아니라 **터치 재채점**
  (`regrade_current`)에만 반영된다 — 지금도 알림 등급은 재채점값이라 구조상 맞는다.
- 부수 효과로 알림량 감소(최악 구간이 터치의 43%).
- 공수 S~M. **결정 필요(Q1)**.

### P3. 알림량 — 게이트 상향 vs 지연 감점
현재 6.67/일. 목표 ≤5/일.
| 안 | 결과 | 부작용 |
|---|---|---|
| a. `alert_min_grade` C→B | **3.0/일** | 과하게 줄어듦. C 중 쓸 만한 것도 차단 |
| b. **P2 지연 감점만 적용** | 추정 4~5/일 | 근거 있는 컷. 추천 |
| c. 둘 다 | 2/일 미만 | 과함 |
**추천: b 먼저, 2주 관찰 후 부족하면 a.** **결정 필요(Q2)**.

### P4. 등급 경계 재보정 — 목적을 "표시 정상화"로 한정
v5 이후 S·A 발급 0건(최고 62점). 예측력은 못 올리지만 **라벨이 죽어 있는 건 여전히 문제**.
- **A≥55 / B≥47 / C≥40** — 알림량을 전혀 늘리지 않으면서(통과 건수 동일) A 등급을 부활시키는 조합.
- **단, P2 를 먼저 넣고 그다음에** 해야 한다(감점이 점수 분포를 바꾸므로).
- 공수 S. **결정 필요(Q3)**.

### P5. 뉴스 쿼터를 "도착순"에서 "중요도순"으로
00~04시에 먼저 온 5건이 쿼터를 다 쓴다. 브리핑은 하루 한 번이므로 **하루치를 모아
발송 직전에 상위 5건을 고르면** 된다 — 큐는 이미 그렇게 쌓이고 있다.
- 중요도 = 촉매 점수(이미 구현된 `_catalyst_sentence` 점수 재사용) + 감시 중 코인 관련성.
- 상한을 늘릴 필요 없음(알림 수 불변).
- 공수 S. 결정 불필요(브리핑 내부 표시 순서 문제).

### P6. 텔레그램 리액션으로 사후 결과 표시 (Bot API 10.0, 2026-05-08)
기존 봇 토큰으로 **자기 메시지에 이모지 반응**을 달 수 있다. 진입 알림 메시지에
나중에 결과를 ✅/❌ 로 붙이면 **새 알림 없이** 사후 확인이 된다.
- 알림 수 증가 0. 스크롤을 거슬러 올라가면 어떤 신호가 맞았는지 한눈에 보인다.
- 리스크: 메시지 ID 보관 필요(이미 `preview_message_id` 전례 있음), API 실패는 무해.
- 공수 M. **결정 필요(Q4)** — 양식 변화는 아니지만 새 상호작용이라 확인받는 게 맞다.

### P7. 빗썸 공개 API 교차검증 (보류 권고)
업비트 단일 소스 의존 완화. 다만 **무료 한도·안정성 미검증**이고 현재 업비트 장애로
문제가 생긴 사례가 없다. **근거 부족 — 보류.**
