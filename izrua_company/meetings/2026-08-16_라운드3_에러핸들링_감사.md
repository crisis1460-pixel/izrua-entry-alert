## HIGH

### F-01 · `monitor/price_check.py:~327` — 잘못된 딕셔너리 키 (실버그)

`_backfill_supply_1h()` 가 `_deriv.get("funding")` 를 읽는다. 그런데 `monitor/binance.py` 의 `fetch_deriv_snapshot()` 는 CoinGecko `"funding_rate"` 필드를 `"fr"` 로 매핑해 반환한다 — `"funding"` 키는 딕셔너리에 존재하지 않는다.

결과: `_funding` 이 항상 `None` → 1h 수급 backfill 판정이 펀딩 입력 없이 수행되거나 `(None, None)` 폴백으로 스킵됨. 과거 터치들의 supply verdict 재판정 데이터 품질 저하.

**수정**: `.get("funding")` → `.get("fr")` (단 1행)

## MEDIUM

### F-02 · `storage/alert_ledger.py:55-62` — `append()` docstring 약속 불이행

docstring: "실패해도 예외를 올리지 않는다". 실제론 `OSError` 만 catch.

`json.dumps(entry)` 는 현재 표준 타입만 사용하므로 `TypeError` 가능성은 낮지만, 약속을 지키지 않는 API 는 미래 변경 시 무언의 함정이 된다. `price_check.py` 에서 `alert_ledger.append()` 는 try/except 없이 직접 호출되므로 예외 탈출 시 회차가 죽는다.

**수정**: `except OSError` → `except Exception  # noqa: BLE001` 으로 확장.

### F-03 · `storage/alert_ledger.py:93-107` — `merge_files()` OS 예외 미처리

`open(tmp, "w")` 와 `os.replace()` 에 try/except 없음. 디스크 오류·권한 오류 시 GitHub Actions 워크플로 스텝이 그대로 죽는다. `merge_files()` 는 워크플로 스텝에서 직접 호출되므로 상위 catch 가 없음.

**수정**: 쓰기+교체 블록을 `except OSError` 로 감싸고 경고 로그 후 반환.

### F-04 · `storage/db.py:506-510` — `init_db()` 예외 처리 없음

`conn.executescript(SCHEMA)`, `_migrate(conn)`, `_backfill_volume_watch_urls()`(L1141), `_backfill_outcome_chain()`(L1167) 전부 예외 처리 없음. 스키마 충돌·DB 오염 시 예외가 그대로 전파 → 봇 전체 정지.

`_backfill_*` 두 함수 내부도 UPDATE 루프에 per-row 예외 처리 없음(L1141, L1167). 행 단위 실패가 backfill 전체를 중단시키고 `init_db()` 를 통해 초기화를 막는다.

**수정 방향**: `_backfill_*` 루프에 per-row `except Exception` 추가; `init_db()` 자체는 호출부(수집 회차 시작)가 감쌀 수 있으나, backfill 함수가 내부에서 격리하는 것이 더 안전.

### F-05 · `collector/coingecko.py:437-442` — `_save_cache()` 비대칭 예외 처리

`_save_json_cache()` 는 `except OSError` 로 쓰기 실패를 삼키지만, `_save_cache()` 에는 try/except 가 전혀 없다. `build_universe()` 말미에서 `_save_cache()` 를 직접 호출하므로 디스크 오류 시 `build_universe()` 가 죽는다. `.tmp` 파일이 잔류할 수도 있다.

**수정**: `_save_cache()` 쓰기 블록을 `except OSError` 로 감싸고 경고 로그.

## LOW

### F-06 · `storage/db.py:224-235` — `connect()` 명시적 rollback 없음

`except` 블록 없이 `finally: conn.close()` 에만 의존. SQLite는 commit 없이 close 되면 자동 rollback하므로 동작은 정확하지만, 코드만 읽어서는 rollback 보장을 알 수 없다. 혼동 유발 가능.

**권고**: `except: conn.rollback(); raise` 를 명시적으로 추가하거나 docstring에 "자동 rollback 의존" 설명 추가.

### F-07 · `storage/db.py:1141,1167` — backfill 루프 per-row 예외 처리 없음

F-04 의 세부 항목. `_backfill_volume_watch_urls()` 와 `_backfill_outcome_chain()` 의 UPDATE 루프는 행 단위 실패를 격리하지 않는다.

### F-08 · `collector/tradingview.py:163` — `# noqa: BLE001` 주석 누락

`_ensure_cookie()` 의 `except Exception as e:` 에 noqa 주석 없음. 기능 문제 없음. 스타일 비일관성.

### F-09 · `collector/telegram_source.py:149` — `# noqa: BLE001` 주석 누락

`_get()` 의 `except Exception as e:` 에 noqa 주석 없음. F-08 과 동일 패턴. "curl_cffi/requests 예외 계열이 달라 광범위 캐치" 의도가 주석으로 설명되어 있으나 noqa 는 없음.

## INFO (설계 제약, 버그 아님)

### I-01 · `monitor/options.py`, `monitor/liquidation.py` — in-memory TTL 무의미

`_cache` dict 가 모듈 레벨 메모리에만 존재. GitHub Actions 는 매 2분 실행이 새 프로세스이므로 5분 TTL 이 사실상 항상 만료된 상태. 설계 의도는 "같은 회차 내 중복 호출 방지" 이므로 실운영 문제 없음. DB meta 캐시로 교체하면 절약 가능하지만 API 횟수 자체가 적어 불필요.

### I-02 · `collector/telegram_source.py:_last_fetch_at` — 프로세스 재시작 시 레이트 리밋 리셋

`_last_fetch_at` 가 메모리에만 있고 `restore_block_state()` 는 `_blocked_until` 만 복원. 재시작 후 채널 폴링 레이트 리밋이 초기화되지만 실운영 영향 미미.
